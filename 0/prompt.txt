# Finish #12895: encrypted sync files and hardware-backed backups

## Configuration and behavior

- Add `encrypt = true` to dotfile policies, defaulting to false. It protects tracked file contents and source files used by copy, symlink, and template entries during publication.
- Use **one shared public-recipient list**, `[history.encryption].recipients`, for all encrypted synced files. No per-file overrides.
- Keep backup recipients in machine-local `[history.origin]` configuration. Existing `origin set --recipient` continues to configure backups.
- Files, rendered outputs, and local recovery history remain plaintext locally.
- Missing keys or failed decryption pause applying and publishing for the whole setup. Fetching and local history continue. Report which files require unlocking without exposing their contents.

Example:

```toml
[history.encryption]
recipients = ["<mac-public-recipient>", "<linux-public-recipient>"]

[dotfiles]
"~/.config/app/credentials" = { mode = "track", encrypt = true }
```

## Encrypted file synchronization

- Encrypt selected file contents before building a publication commit. Preserve logical filenames; document that paths, configuration, and recipient public keys remain visible.
- Store versioned encrypted envelopes at their existing branch paths. Bind each envelope to its logical path and original file mode.
- Upgrade the setup repository marker when encrypted files are first published. Read existing format-1 repositories; older clients must reject the new format rather than apply ciphertext as files.
- Decrypt upstream files before the existing reconciliation and conflict logic. Keep plaintext comparison state local and ciphertext publication state separate. Reuse ciphertext when content, mode, and recipients are unchanged so repeated syncs produce no churn.
- Preserve existing conflict decisions and configuration validation. Never apply ciphertext to a destination or merge ciphertext as text.
- Encrypt template sources before publication and decrypt before rendering. Reject `encrypt = true` for inline `content`/`block` declarations, whose secrets would otherwise remain in shared configuration; direct users to external sources.
- Preserve privacy exclusions: encryption does not implicitly enable sharing of private files. Reject overlapping declarations that would publish the same source both encrypted and plaintext.
- Prevent backup bypasses: files marked encrypted must be excluded from plaintext remote backups, including when rebuilding older checkpoints. They may enter encrypted backups under that machine’s backup recipients.
- Recipient changes re-encrypt all current encrypted files in one leased branch update. Missing decryption access blocks the change. Explain that changing encryption cannot erase plaintext or revoked recipients’ access from earlier Git history and clones.

## Hardware-backed identities

- Support user-installed age plugins for Secure Enclave and Linux TPM through the existing recipient and identity configuration.
- Users install plugins and generate hardware identities themselves. Accept software and hardware recipients together; hardware-only lists are allowed with a device-loss warning.
- Run plugins only from locally accepted configuration, never from arbitrary remote envelope instructions.
- Interactive sync/pull and rollback may request hardware authorization. Watchers and routine diagnostics remain noninteractive; required authorization pauses progress with an actionable message.
- Keep local plaintext caches, as selected. Hardware authorization protects decryption of incoming content, not subsequent access to local copies.
- Report hardware identities as configured but unverified during routine diagnostics. Do not trigger Touch ID or PIN prompts to test restorability.
